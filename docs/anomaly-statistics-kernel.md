# Anomaly statistics kernel — mechanism

This document describes the mechanism of the anomaly statistics kernel.

- **A qualification kernel, not a detector.** Its caller owns the policy. It holds a robust deviation (median/MAD, `1.4826` scaling, `log1p` for counts and identity for rates), an empirical two-sided tail rank (`p = (1 + count at least as extreme) / (n + 1)`, ties counted into both tails), and a policy-feasibility check (`min_references_for(alpha) == ceil(2/alpha) - 1`). Every function is pure — no clock, no randomness, no logging, no I/O, no global state — so a replay over historical data qualifies the method itself so a caller can depend on it. It is a sibling of `performance_validator.py`, never a patch to it: that module's `_two_sample_t_test` discards its own degrees of freedom and falls back to a normal approximation, and nothing here imports it.
- **It carries no operating thresholds.** What counts as a dip, how many references are enough, what alpha an epoch may spend — all of that is caller policy. The kernel only reports what is *attainable*, and refuses by type when the arithmetic would have to invent something: `NO_BASELINE_VARIATION` when the scaled MAD is 0 (no epsilon, no weaker fallback — the returned `Refusal` has nowhere to put a deviation), `INSUFFICIENT_RESOLUTION` when the method's own floor `2/(n+1)` cannot meet the allocated alpha, and `POLICY_INFEASIBLE` when the error budget, the registered-test count and the reference cap contradict each other before any outcome is inspected (ten tests at total alpha 0.05 need 399 references each, against a 200 cap). A zero raw reference median makes `relative_effect` `None`, never `0` and never infinite. Malformed input — NaN, infinity, an empty reference, an unnamed transform — is a caller bug and raises `ValueError` rather than being dressed as a statistical refusal.

## Volume controller

`analytics/volume_controller.py` is the pure decision function for shorts per LF, LF days per region and shorts times; `analytics/volume_policy.py` holds its named rails under `POLICY_REV`. Shorts per LF, LF days and posting times are Waypost's decisions, computed from analytics every night, so the rails are policy revisions in code, never per-run config.

- **`decide(evidence, states, now) -> list[Decision]`** has no I/O, clock or randomness. One knob moves per call, by one step; every other knob holds with a code from a fixed vocabulary (`INSUFFICIENT_EVIDENCE`, `CONFIRMING`, `COOLDOWN`, `IN_DEADBAND`, `AT_FLOOR`, `AT_CEILING`, `JOINT_CEILING`, `LEARNED_CEILING`, `ROLLBACK_LOCKOUT`, `SUPPLY_BOUND`, `NO_BASELINE_VARIATION`, `STATE_UNREADABLE`, `ANALYTICS_<status>`). `Decision.state_patch` + `apply_decision` is the state transition; persistence is the caller's.
- **Sample sizes are derived**: down needs `min_references_for(0.20)` (9), up needs `min_references_for(0.05)` (39) and two distinct cohorts. A `Refusal` from the kernel becomes the hold's reason code, never a number.
- **Probation** judges every applied change on a post-change cohort against its baseline with `robust_deviation` (log1p): more than 2 scaled MAD below rolls back (lockout `cooldown x 2^k`, 112 d cap; learned ceiling at a failed up-step for 90 d), else it validates. Analytics not ok, or 21 d without a settled short, steps toward `last_validated`, never past it.
- **Joint rails**: shorts/LF 7-10, LF days 1-3 per region and 4 per week, 30 shorts/week across regions, so no reachable pair nears 14 shorts/LF, the rate that is kept out of reach (a test pins it).
